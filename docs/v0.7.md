# v0.7 — Event Bus

## 这一章解决什么问题

到目前为止，一个 Plugin 想知道另一个 Plugin 发生了什么事，只能靠共享 Context 上的 service 直接调用——Producer 得知道 Consumer 是谁、Consumer 得知道 Producer 提供了什么方法。这一章加入 Event Bus，让 Producer 和 Consumer 完全不需要认识对方，只需要约定一个事件名字。

## 上一版本有什么不足

假设要让 Logger 在每次 Greeter 打招呼之后记一笔日志，上一章为止的做法只能是：Logger 直接 `ctx.get('greeter')` 拿到 greeter 对象，包一层代理方法，或者反过来让 Greeter 主动认识 Logger、调用它的方法——不管哪种做法，两个原本无关的 Plugin 都会因此耦合在一起。

## 本章设计

目标 API：

```ts
ctx.on('greet', handler)
ctx.emit('greet', payload)
```

内部结构：

```ts
Map<string, Set<Listener>>
```

### 本章唯一的关键要求：on() 必须自动成为 Effect

`ctx.on(...)` 不能只是"把 listener 加进 Set 里"，还必须知道怎么把它移除。做法是让 `on()` 内部直接调用 `this.effect(...)`：

```ts
on(event: string, listener: Listener): void {
  this.effect(() => {
    let set = this.listeners.get(event)
    if (!set) {
      set = new Set()
      this.listeners.set(event, set)
    }
    set.add(listener)

    return () => {
      set!.delete(listener)
    }
  })
}
```

因为 `effect()` 记到的是 `currentScope`（上一章建立的机制），如果这次 `on()` 调用发生在某个 Plugin 的安装过程中，这个 listener 的移除逻辑就自动归属于那个 Plugin 的 scope——Plugin 被卸载时，`scope` 里的 cleanup 被逐一执行，其中就包括"把这个 listener 从 Set 里删掉"，完全不需要手写 `off()`。

这是这一章最重要的设计洞察：**Event Listener 本身也是一种 Effect**，和"provide 一个 service、卸载时 remove 它"是同一个模型，只是这次的"setup"是 `set.add(listener)`，"cleanup"是 `set.delete(listener)`。前面章节建立的 `effect`/`scope` 机制不需要为 Event 专门改造，直接复用。

## 最小实现

`src/event.ts`：

```ts
export type Listener = (...args: any[]) => void
```

`src/context.ts` 新增：

```ts
private listeners = new Map<string, Set<Listener>>()

on(event: string, listener: Listener): void {
  this.effect(() => {
    let set = this.listeners.get(event)
    if (!set) {
      set = new Set()
      this.listeners.set(event, set)
    }
    set.add(listener)
    return () => { set!.delete(listener) }
  })
}

emit(event: string, ...args: unknown[]): void {
  const set = this.listeners.get(event)
  if (!set) return
  for (const listener of set) {
    listener(...args)
  }
}
```

`emit` 对没有任何 listener 的事件直接返回，不报错——延续本书一贯的"缺失是常态，不是异常"原则。

## 测试

```ts
it('dispose plugin 后，它注册的 listener 自动消失', () => {
  const ctx = new Context()
  const calls: string[] = []

  const loggerPlugin: Plugin = (ctx) => {
    ctx.on('greet', (name: string) => {
      calls.push(`[LOG] greeted ${name}`)
    })
  }

  const disposeLogger = ctx.plugin(loggerPlugin)
  ctx.emit('greet', 'Alex')
  expect(calls).toEqual(['[LOG] greeted Alex'])

  disposeLogger()
  ctx.emit('greet', 'Alex')

  expect(calls).toEqual(['[LOG] greeted Alex']) // 没有增加
})

it('Greeter emit greet，Logger 监听 —— 两者互不知道对方存在', () => {
  const ctx = new Context()
  const logs: string[] = []

  const greeterPlugin: Plugin = (ctx) => {
    ctx.effect(() => {
      ctx.provide('greeter', {
        greet(name: string) {
          const message = `Hello, ${name}!`
          ctx.emit('greet', name)
          return message
        },
      })
      return () => ctx.remove('greeter')
    })
  }
  const loggerPlugin: Plugin = (ctx) => {
    ctx.on('greet', (name: string) => logs.push(`[LOG] greeted ${name}`))
  }

  ctx.plugin(greeterPlugin)
  ctx.plugin(loggerPlugin)

  const greeter = ctx.get('greeter') as { greet(name: string): string }
  const message = greeter.greet('Alex')

  expect(message).toBe('Hello, Alex!')
  expect(logs).toEqual(['[LOG] greeted Alex'])
})
```

运行：

```bash
npm test
```

实际输出：

```text

      Tests  28 passed (28)
```

## Demo

```ts
import { Context } from './src/context'
import type { Plugin } from './src/plugin'

const greeterPlugin: Plugin = (ctx) => {
  ctx.effect(() => {
    ctx.provide('greeter', {
      greet(name: string) {
        const message = `Hello, ${name}!`
        ctx.emit('greet', name)
        return message
      },
    })
    return () => ctx.remove('greeter')
  })
}

const loggerPlugin: Plugin = (ctx) => {
  ctx.on('greet', (name: string) => {
    console.log(`[LOG] greeted ${name}`)
  })
}

const ctx = new Context()
ctx.plugin(greeterPlugin)
const disposeLogger = ctx.plugin(loggerPlugin)

const greeter = ctx.get('greeter') as { greet(name: string): string }
console.log(greeter.greet('Alex'))

disposeLogger()
console.log('--- logger disposed, greet again ---')
console.log(greeter.greet('Alex'))
```

实际输出：

```text
[LOG] greeted Alex
Hello, Alex!
--- logger disposed, greet again ---
Hello, Alex!
```

第二次 `greet()` 之后没有 `[LOG]` 行——`disposeLogger()` 卸载后，listener 已经从 `Set` 里被移除，`emit` 找不到任何 listener 可以调用。

## 这一章之后

- `emit()` 是同步的，listener 抛异常会中断后面的 listener 执行——真实场景里一个 listener 出错不应该拖累其他 listener，这个问题留给 Plugin Failure Isolation 那一章。
- 没有 `once()`（只触发一次自动移除的 listener）、没有更精细的事件分发语义，这一章只做最基础的"广播给所有 listener"。
- `emit` 的参数类型是 `unknown[]`，`Listener` 类型是 `(...args: any[]) => void`——事件名和参数类型之间没有任何静态检查，写错事件名或参数个数只有运行时才会发现。

## 思考题

1. `on()` 内部调用 `this.effect(...)`，意味着如果在 Context 根级别（不在任何 `plugin()` 内部）直接调用 `ctx.on(...)`，这个 listener 会被记到哪个 scope？只有 `ctx.dispose()` 能移除它，还是有别的办法？
2. 如果两个不同的 Plugin 都 `ctx.on('greet', ...)`，注册了各自的 listener，卸载其中一个 Plugin，另一个的 listener 会受影响吗？为什么（提示：`Set<Listener>` 和上一章的 scope 隔离机制是怎么配合的）？
3. 这一章的 `emit()` 一旦某个 listener 抛异常，`for...of` 循环会直接中断，后面排在它之后的 listener 不会被调用。设想一个具体场景（比如 Logger 和 Analytics 都监听 `greet`，Logger 先注册但抛了异常），说明这会造成什么后果。
