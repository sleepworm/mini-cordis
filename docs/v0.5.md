# v0.5 — Reversible Effect

> 这是整个 MiniCordis 最重要的 commit 之一。

## 这一章解决什么问题

上一章让 Plugin 能"安装"东西，但装完就再也撤不回去了——`ctx.provide('greeter', ...)` 调用之后，没有任何办法把这个动作反过来。这一章要回答：**Plugin 造成的改变，怎么撤销？**

## 上一版本有什么不足

`ctx.plugin(greeterPlugin)` 跑完之后，`ctx.has('greeter')` 永远是 `true`，除非有人手动调用 `ctx.remove('greeter')`——但"手动记得调用"不是一个可靠的机制，而且 Plugin 内部到底 `provide` 了几个 service，调用方根本无从知道，更别说逐一撤销。

## 本章设计

目标 API：

```ts
ctx.effect(() => {
  // setup：做一些改变
  return () => {
    // cleanup：撤销上面的改变
  }
})
```

`effect()` 立即执行 `setup`；如果 `setup` 返回了一个函数（cleanup），就把它记下来。`ctx.dispose()` 把记下来的所有 cleanup 依次执行一遍。

```text
Context
└── cleanups[]
      ├── cleanup A
      ├── cleanup B
      └── cleanup C
```

### 一个隐藏的设计决策：撤销顺序

`dispose()` 按**后进先出**（LIFO）执行 cleanup，不是按注册顺序。这不是随便选的——如果 effect B 是在 effect A 之后注册的，B 很可能依赖了 A 已经建立好的状态（比如 A `provide` 了一个 service，B 的 setup 里用到了它）。撤销的时候如果先撤 A 再撤 B，B 的 cleanup 执行时它依赖的东西可能已经没了。后进先出保证"后建立的先撤销"，对称于"先建立的先决条件更基础、应该活得更久"这个直觉。

### Greeter 改造成可逆

```ts
const greeterPlugin: Plugin = (ctx) => {
  ctx.effect(() => {
    ctx.provide('greeter', { greet: (name: string) => `Hello, ${name}!` })
    return () => {
      ctx.remove('greeter')
    }
  })
}
```

`provide` 和它对应的 `remove` 现在写在一起——setup 做什么，cleanup 就撤销什么，两者在代码里紧挨着，不容易漏写。

## 最小实现

`src/context.ts` 新增：

```ts
type Cleanup = () => void
type EffectSetup = () => Cleanup | void

export class Context {
  // ...既有的 services / provide / get / has / remove / plugin
  private cleanups: Cleanup[] = []

  effect(setup: EffectSetup): void {
    const cleanup = setup()
    if (cleanup) {
      this.cleanups.push(cleanup)
    }
  }

  dispose(): void {
    while (this.cleanups.length) {
      const cleanup = this.cleanups.pop()!
      cleanup()
    }
  }
}
```

## 测试

```ts
it('dispose 会执行 cleanup', () => {
  const ctx = new Context()
  let disposed = false

  ctx.effect(() => {
    return () => { disposed = true }
  })

  expect(disposed).toBe(false)
  ctx.dispose()
  expect(disposed).toBe(true)
})

it('多个 cleanup 按后进先出的顺序执行', () => {
  const ctx = new Context()
  const order: number[] = []

  ctx.effect(() => () => order.push(1))
  ctx.effect(() => () => order.push(2))
  ctx.effect(() => () => order.push(3))

  ctx.dispose()

  expect(order).toEqual([3, 2, 1])
})

it('重复调用 dispose 是安全的 no-op', () => {
  const ctx = new Context()
  let count = 0
  ctx.effect(() => () => { count += 1 })

  ctx.dispose()
  ctx.dispose()

  expect(count).toBe(1)
})

it('greeter plugin 改造成可逆之后，dispose 会移除它 provide 的 service', () => {
  const ctx = new Context()
  const greeterPlugin: Plugin = (ctx) => {
    ctx.effect(() => {
      ctx.provide('greeter', { greet: (name: string) => `Hello, ${name}!` })
      return () => ctx.remove('greeter')
    })
  }

  ctx.plugin(greeterPlugin)
  expect(ctx.has('greeter')).toBe(true)

  ctx.dispose()
  expect(ctx.has('greeter')).toBe(false)
})
```

`重复调用 dispose 是安全的 no-op` 这条延续了上一章定下的一致性原则——`remove()` 对不存在的东西是 no-op，`dispose()` 对已经清空的 `cleanups` 也应该是 no-op，不应该重复执行副作用或报错。

## Demo

```ts
import { Context } from './src/context'
import type { Plugin } from './src/plugin'

const greeterPlugin: Plugin = (ctx) => {
  ctx.effect(() => {
    ctx.provide('greeter', { greet(name: string) { return `Hello, ${name}!` } })
    return () => {
      ctx.remove('greeter')
    }
  })
}

const ctx = new Context()
ctx.plugin(greeterPlugin)
console.log('has after plugin:', ctx.has('greeter'))

ctx.dispose()
console.log('has after dispose:', ctx.has('greeter'))
```

实际输出：

```text
has after plugin: true
has after dispose: false
```

## 这一章之后

- `ctx.dispose()` 会撤销**这个 Context 上所有的** effect，不分是哪个 Plugin 注册的。如果只想撤销某一个 Plugin（比如只卸载 Greeter，保留 Logger），现在做不到——这正是下一章（Plugin Scope）要解决的问题。
- `effect()` 只支持同步 setup。真实场景里，"启动"这件事经常是异步的（比如要连接一个远程服务），这一版完全没考虑。
- cleanup 本身如果抛异常，会中断整个 `dispose()` 循环里后面的 cleanup——这是一个已知但暂时不处理的问题，留给后面 Plugin failure isolation 章节。

## 思考题

1. 为什么 `dispose()` 要用后进先出的顺序，而不是先进先出？试着构造一个具体场景（两个 effect，一个依赖另一个建立的状态），说明如果顺序反过来会出什么问题。
2. `effect()` 的返回类型是 `Cleanup | void`——setup 可以选择"不需要 cleanup"。什么样的 setup 是合理的、不需要返回 cleanup 的？举一个例子。
3. 现在 `ctx.dispose()` 会清空**这个 Context 上所有的** effect。如果你现在就想让 `greeterPlugin` 和 `loggerPlugin` 能被分别撤销，你会怎么改 `plugin()`/`effect()` 的接口？（不用写代码，描述思路即可——下一章会正式解决这个问题，先自己想一版方案，再对比实际实现有什么不同。）
