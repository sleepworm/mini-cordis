# v0.9 — Reactive Dependency Lifecycle

> 这是另一个核心 commit。这是 MiniCordis 第一次真正变成一个 Dynamic Runtime，而不只是一个 DI Container。

## 这一章解决什么问题

上一章的 `ctx.require()` 只能回答"此刻依赖满不满足"，回答完就结束了——依赖后来变了，`require()` 一无所知。这一章要做到这个完整循环：

```text
Greeter unavailable
      ↓
App inactive

Greeter installed
      ↓
App active

Greeter removed
      ↓
App cleanup

Greeter installed again
      ↓
App active again
```

## 上一版本有什么不足

`ctx.require()` 是"一次性快照"：调用的那一刻检查一遍，之后 Context 完全不记得"谁依赖过什么"。如果 Greeter 后来被卸载，之前跑过的 `require()` callback 不会有任何反应——它已经执行完了，`require()` 本身没有留下任何可以在未来被重新触发的东西。

## 本章设计

目标 API：

```ts
ctx.inject(['greeter'], (ctx) => {
  // 依赖满足时执行；依赖消失时，这段代码造成的一切会被自动撤销；
  // 依赖再次满足，会重新执行一遍
})
```

### 核心机制：把"安装"和"响应式激活"统一成同一件事

这一章最关键的设计决策是：**`inject()` 的"激活"，用的是和 `plugin()` 完全一样的 scope 机制**。回顾 Plugin Scope 那一章，`plugin(fn)` 做的事情是"开一个新 scope、跑 fn、记住怎么撤销"；这一章把这个动作抽成一个私有方法 `runInScope()`，`plugin()` 和 `inject()` 的"激活"都调用它：

```ts
private runInScope(fn: (ctx: Context) => void): () => void {
  const parentScope = this.currentScope
  const scope: Cleanup[] = []

  this.currentScope = scope
  try {
    fn(this)
  } finally {
    this.currentScope = parentScope
  }

  let disposed = false
  return () => {
    if (disposed) return
    disposed = true
    while (scope.length) {
      scope.pop()!()
    }
  }
}
```

对 Context 来说，"安装一个 Plugin"和"依赖满足后激活一段代码"**没有本质区别**——都是"打开一个可撤销的 scope，跑一段代码，记住怎么把它撤回去"。区别只在于：Plugin 装上去就立刻激活一次，不会再撤销重激活；`inject()` 的 callback 会随着依赖的存在与否反复"激活 → 撤销 → 再激活"。

### 依赖状态怎么被追踪

每个 `inject()` 调用创建一条 `Injection` 记录：

```ts
interface Injection {
  names: string[]
  callback: (ctx: Context) => void
  dispose: (() => void) | null // 非 null 说明当前处于激活状态
}
```

`Context` 维护一个 `injections: Set<Injection>`。**`provide()` 和 `remove()` 现在都会触发 `reevaluateAll()`**——重新检查每一条 Injection：依赖满足且还没激活 → 激活；依赖不满足且当前激活着 → 撤销。这一版故意用最简单的"全量重新检查"，不做增量的"反向索引"，因为 MiniCordis 的教学规模下 Injection 数量不会大到需要优化，简单直接比性能更重要。

```ts
provide(name: string, service: unknown): void {
  this.services.set(name, service)
  this.reevaluateAll()
}

remove(name: string): void {
  this.services.delete(name)
  this.reevaluateAll()
}
```

## 最小实现

完整的 `inject()` 及其支撑方法：

```ts
inject(names: string[], callback: (ctx: Context) => void): () => void {
  const injection: Injection = { names, callback, dispose: null }
  this.injections.add(injection)
  this.reevaluate(injection)

  let disposed = false
  const dispose = () => {
    if (disposed) return
    disposed = true
    this.deactivate(injection)
    this.injections.delete(injection)
  }

  this.currentScope.push(dispose)
  return dispose
}

private isSatisfied(injection: Injection): boolean {
  return injection.names.every((name) => this.has(name))
}

private activate(injection: Injection): void {
  if (injection.dispose) return
  injection.dispose = this.runInScope(injection.callback)
}

private deactivate(injection: Injection): void {
  if (!injection.dispose) return
  const dispose = injection.dispose
  injection.dispose = null
  dispose()
}

private reevaluate(injection: Injection): void {
  if (this.isSatisfied(injection)) {
    this.activate(injection)
  } else {
    this.deactivate(injection)
  }
}

private reevaluateAll(): void {
  for (const injection of this.injections) {
    this.reevaluate(injection)
  }
}
```

`inject()` 返回的 `dispose` 和 `plugin()` 一样被推进 `currentScope`——所以 `inject()` 也支持被外层 scope 级联撤销，和前面章节建立的 Ownership 模型完全一致。

同时，`plugin()` 也顺手用上了 `runInScope()`，代码变短了：

```ts
plugin(fn: Plugin): () => void {
  const parentScope = this.currentScope
  const dispose = this.runInScope(fn)
  parentScope.push(dispose)
  return dispose
}
```

## 测试

```ts
it('完整生命周期：missing → added → active → removed → disposed → added again → active again', () => {
  const ctx = new Context()
  const log: string[] = []

  const dispose = ctx.inject(['greeter'], (ctx) => {
    log.push('active')
    ctx.effect(() => () => log.push('disposed'))
  })
  expect(log).toEqual([]) // missing

  ctx.provide('greeter', {})
  expect(log).toEqual(['active']) // added → active

  ctx.remove('greeter')
  expect(log).toEqual(['active', 'disposed']) // removed → disposed

  ctx.provide('greeter', {})
  expect(log).toEqual(['active', 'disposed', 'active']) // added again → active again

  dispose()
})

it('App inject greeter，Greeter 通过 plugin 加载/卸载/重新加载，App 自动跟着变化', () => {
  const ctx = new Context()
  const log: string[] = []

  ctx.inject(['greeter'], (ctx) => {
    const greeter = ctx.get('greeter') as { greet(name: string): string }
    log.push(greeter.greet('Alex'))
  })

  const greeterPlugin: Plugin = (ctx) => {
    ctx.effect(() => {
      ctx.provide('greeter', { greet: (name: string) => `Hello, ${name}!` })
      return () => ctx.remove('greeter')
    })
  }

  expect(log).toEqual([])

  const disposeGreeter = ctx.plugin(greeterPlugin)
  expect(log).toEqual(['Hello, Alex!'])

  disposeGreeter()
  ctx.plugin(greeterPlugin)
  expect(log).toEqual(['Hello, Alex!', 'Hello, Alex!'])
})
```

## Demo

```ts
import { Context } from './src/context'
import type { Plugin } from './src/plugin'

const ctx = new Context()

ctx.inject(['greeter'], (ctx) => {
  console.log('App active')
  ctx.effect(() => {
    return () => console.log('App cleanup')
  })
})

const greeterPlugin: Plugin = (ctx) => {
  ctx.effect(() => {
    ctx.provide('greeter', { greet(name: string) { return `Hello, ${name}!` } })
    return () => ctx.remove('greeter')
  })
}

console.log('--- Greeter installed ---')
let disposeGreeter = ctx.plugin(greeterPlugin)

console.log('--- Greeter removed ---')
disposeGreeter()

console.log('--- Greeter installed again ---')
disposeGreeter = ctx.plugin(greeterPlugin)
```

实际输出：

```text
--- Greeter installed ---
App active
--- Greeter removed ---
App cleanup
--- Greeter installed again ---
App active
```

## 这一章之后

- `reevaluateAll()` 每次 `provide`/`remove` 都全量扫描所有 Injection，没有按依赖名字建反向索引。规模大了会是性能问题，但这不是这一版要操心的事。
- 没有处理"Injection 的 callback 自己又调用 `ctx.provide()`/`ctx.remove()`"这种递归场景的正确性保证——理论上会触发嵌套的 `reevaluateAll()`，这一版没有专门测试过这种情况，行为未定义。
- `inject()` 依赖多个名字时（比如 `['clock', 'greeter']`），任何一个变化都会触发整条重新评估——没有"只有真正相关的那个 Injection 才被检查"这种精细化调度，这是上面提到的"没做反向索引"的直接后果。

## 思考题

1. `provide()`/`remove()` 触发的 `reevaluateAll()` 是全量扫描。设想一下，如果 MiniCordis 有 100 个 Injection，其中只有 1 个依赖了这次 `provide()` 的那个 service，其余 99 个完全不相关——这次 `reevaluateAll()` 做了多少"无用功"？你会怎么设计一个反向索引来避免这些无用功（不用写代码，说清楚数据结构和更新时机）？
2. 写一个测试：`Greeter` 用 `ctx.inject(['clock'], ...)` 声明依赖 `clock`，验证只卸载 `clock`、不碰 `greeter` 时，`greeter` 是否会级联失效。
3. 如果 `inject()` 的 callback 在被激活时抛出异常（比如 `ctx.inject(['greeter'], () => { throw new Error('boom') })`），现在的实现会发生什么？`activate()` 里 `runInScope()` 调用 `fn(this)` 时没有任何 try/catch——这个异常会一路冒泡到谁那里？这是不是一个需要在后面章节（Plugin failure isolation）解决的问题？
4. 这一章说"`plugin()` 装一次，激活一次，不会再撤销重激活"。如果想让 Plugin 本身也具备"依赖满足才激活、依赖消失就撤销"的能力（而不是只有 `inject()` 才有这个能力），你会怎么改 `plugin()` 的签名和实现？（提示：`Plugin` 类型现在是 `(ctx: Context) => void`，需要带上依赖声明。）
