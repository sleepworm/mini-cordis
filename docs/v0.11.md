# v0.11 — Child Context

## 这一章解决什么问题

到目前为止，MiniCordis 里只有一个 Context——所有 Plugin 共享同一份 service 表、同一个事件总线。真实场景里经常需要"局部"的 Runtime：比如一个 Agent Harness 里，每个 Session 可能需要自己的一套 `model`/`tools` 配置，但又该能共用一些全局的东西（比如 `telemetry`）。这一章加入 `ctx.fork()`，第一次让 Context 变成一棵树，而不是一个孤立的点。

## 上一版本有什么不足

假设要模拟"两个 Session，各自可能用不同的 Greeter 实现，但共享同一个 Logger"，用上一章为止的工具做不到——只有一个 Context，`provide('greeter', ...)` 全局唯一，两个 Session 没法同时拥有不同版本的同名 service。

## 本章设计

目标 API：

```ts
const child = ctx.fork()
```

第一版规则，只有四条，刻意保持简单：

```text
Child 可以读取 Parent Service
Child 可以注册自己的 Service
Child Service 优先于 Parent
Dispose Child 不影响 Parent
```

### 读取：本地没有就往上问

```ts
get(name: string): unknown {
  if (this.services.has(name)) {
    return this.services.get(name)
  }
  return this.parent?.get(name)
}

has(name: string): boolean {
  return this.services.has(name) || (this.parent?.has(name) ?? false)
}
```

`get`/`has` 都是"先看自己，没有就问 parent"，`parent` 是 `Context | null`（root 的 `parent` 是 `null`，链条到头）。这两条实现同时满足了"Child 可以读取 Parent Service"和"Child Service 优先于 Parent"——本地有就不会继续往上问，天然就是覆盖语义，不需要额外的"覆盖检测"逻辑。

`provide()`/`remove()` **完全不需要改动**——`provide` 永远写本地的 `services` Map，不会碰到 parent；`remove` 删掉本地的覆盖之后，`get`/`has` 自然会重新看到 parent 的版本（因为本地查不到了，往上问就问到了）。这是这一版设计里最省心的一点：前面章节定下的 `provide`/`get`/`has`/`remove` 语义，不需要为了支持继承而重新设计。

### Dispose：child 自己隔离，但被 parent 级联

```ts
fork(): Context {
  const parentScope = this.currentScope
  const child = new Context(this)

  let disposed = false
  const disposeChild = () => {
    if (disposed) return
    disposed = true
    child.dispose()
  }
  parentScope.push(disposeChild)

  return child
}
```

`child` 是一个全新的 `Context` 实例，有自己独立的 `services`/`cleanups`/`listeners`/`injections`——`child.dispose()` 只会撤销这些自己的东西，完全碰不到 `parent` 的任何数据，这就是"Dispose Child 不影响 Parent"，不需要专门写隔离逻辑，两个对象本来就是分开的。

反过来，"parent dispose 时 child 也应该处理"是靠**复用前面章节已经建立的机制**做到的：`disposeChild` 被 `push` 进 `parentScope`，和 `plugin()` 把自己的 `dispose` 塞进父 scope、`inject()` 把自己的 `dispose` 塞进 `currentScope` 是**同一个模式**——父级 `teardown()` 的时候，会把 `disposeChild` 当成普通的一个 cleanup 调用，自动级联撤销 child。这一章没有为"父子级联"发明任何新代码路径。

## 最小实现

新增一个构造函数参数，记录 `parent`：

```ts
constructor(private readonly parent: Context | null = null) {}
```

`get`/`has` 按上面的方式往上问；`fork()` 按上面的方式创建子 Context 并挂进当前 scope。其余方法（`provide`/`remove`/`effect`/`plugin`/`on`/`emit`/`require`/`inject`/`dispose`）一行都没有改动。

## 测试

```ts
it('child 继承 parent 的 service', () => {
  const root = new Context()
  root.provide('shared', 'root-value')
  const child = root.fork()

  expect(child.get('shared')).toBe('root-value')
})

it('child 的同名 service 覆盖 parent 的（child 优先）', () => {
  const root = new Context()
  root.provide('greeter', { greet: () => 'Hello from root' })
  const child = root.fork()
  child.provide('greeter', { greet: () => 'Hello from child' })

  expect((child.get('greeter') as any).greet()).toBe('Hello from child')
  expect((root.get('greeter') as any).greet()).toBe('Hello from root') // root 没被改动
})

it('dispose child 不影响 parent', () => {
  const root = new Context()
  root.provide('shared', 'root-value')
  const child = root.fork()
  child.dispose()

  expect(root.has('shared')).toBe(true)
})

it('dispose parent 时，child 也会被级联 dispose', () => {
  const root = new Context()
  const child = root.fork()

  let childCleaned = false
  child.effect(() => () => { childCleaned = true })

  root.dispose()

  expect(childCleaned).toBe(true)
})
```

再加一个验证"实时性"的用例——`get`/`has` 不是在 `fork()` 那一刻拍快照，而是每次调用都真实往上查：

```ts
it('parent 之后再 provide 新 service，已经 fork 出去的 child 也能读到', () => {
  const root = new Context()
  const child = root.fork()

  expect(child.has('later')).toBe(false)
  root.provide('later', 'value')
  expect(child.has('later')).toBe(true)
})
```

## Demo

```ts
import { Context } from './src/context'

const root = new Context()
root.provide('shared', 'telemetry')
root.provide('greeter', { greet(name: string) { return `Hello, ${name}!` } })

const childA = root.fork()
const childB = root.fork()

childA.provide('greeter', { greet(name: string) { return `Hi ${name}, from A` } })

console.log('childA greeter:', (childA.get('greeter') as any).greet('Alex'))
console.log('childB greeter:', (childB.get('greeter') as any).greet('Alex'))
console.log('childA sees shared:', childA.get('shared'))

childA.dispose()
console.log('--- childA disposed ---')
console.log('root still has greeter:', root.has('greeter'))
console.log('root still has shared:', root.has('shared'))
console.log('childB still has greeter:', childB.has('greeter'))
```

实际输出：

```text
childA greeter: Hi Alex, from A
childB greeter: Hello, Alex!
childA sees shared: telemetry
--- childA disposed ---
root still has greeter: true
root still has shared: true
childB still has greeter: true
```

`childA` 覆盖了 `greeter`，`childB` 完全没受影响，还在用 root 的版本——两个 child 之间也是互相隔离的，不只是"child 不影响 parent"。`childA.dispose()` 之后，root 和 `childB` 都完好无损。

## 这一章之后

- **`inject()` 不会跨越 parent/child 边界响应式生效**：如果 `child.inject(['clock'], ...)` 而 `clock` 是之后才在 **parent** 上 `provide()` 的，`child` 的 `reevaluateAll()` 不会被触发——因为 `provide()` 只会调用**自己所在那个 Context** 的 `reevaluateAll()`，不会通知子孙。`get`/`has` 是"实时往上查"，但"依赖状态变化时主动通知"这件事目前只在同一个 Context 内部生效，没有传播到子树。这是一个真实的、明确记录下来的限制，不是无意间漏掉的。
- 没有 Isolation——同一个名字在不同子树没法完全没有继承关系、互不可见；这一版的 child 永远能看到 parent（除非被覆盖），做不到"完全切断"。
- 事件总线（`listeners`）和 Injection（`injections`）都是每个 Context 各自独立的一份，不会继承——`child.on('greet', ...)` 只能收到 `child.emit('greet', ...)`，收不到 `root.emit('greet', ...)`。

## 思考题

1. `get()`/`has()` 每次调用都要沿着 `parent` 链往上走。如果这条链很长（比如 5 层嵌套的 fork），一次 `get()` 最坏情况要问多少次？这在什么场景下会成为性能问题？
2. 这一章说"`inject()` 不会跨越 parent/child 边界响应式生效"。设想一个具体场景：`root.provide('clock', ...)` 发生在 `child.inject(['clock'], ...)` 注册**之后**——这种情况下，`child` 的 `reevaluateAll()` 真的不会被触发吗？还是说因为触发时机不同，行为其实是对的（提示：`inject()` 内部调用 `this.reevaluate(injection)` 的那一次检查，用的是 `this.has(name)`，这个 `has()` 本身就会往上问 parent）？动手写一个测试验证你的判断。
3. 如果要让 `child.on('greet', ...)` 也能收到 `root.emit('greet', ...)`（事件跨越 parent/child 边界），你会怎么改 `on()`/`emit()`？这个改动会不会和"child 的 listener 应该独立于 parent"这个隔离诉求产生冲突？
