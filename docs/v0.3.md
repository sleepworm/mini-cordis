# v0.3 — Service Removal

## 这一章解决什么问题

上一章的 `Context` 只能"加"，不能"减"——`provide` 之后，一个 service 就永远留在那里了。这一章让 capability 可以消失，这是后面 Lifecycle 章节（依赖消失/恢复时组件自动 deactivate/reactivate）能够存在的前提。

## 上一版本有什么不足

`Map` 里存的东西只增不减。真实场景里——插件被卸载、连接断开、临时资源被回收——capability 消失是常态，不是例外。到目前为止，MiniCordis 还没法表达出"这个能力现在没了"这件事。

## 本章设计

两个新方法：

```ts
ctx.has(name)     // 判断 service 是否存在
ctx.remove(name)  // 移除 service
```

`has()` 单独作为一个方法而不是让调用方自己 `get(name) !== undefined` 去判断，是因为"能力是否存在"和"取出能力"是两个不同的问题——后面章节需要频繁问"这个能力现在存在吗"，而不需要真的把它取出来用，`has()` 让这个意图更明确。

`remove()` 对一个从未 `provide` 过的 name 调用，直接是 no-op，不抛异常——和 `Map.delete()` 本身的行为一致，也符合"卸载一个不存在的东西"在实践中通常不该是错误这个直觉。

## 最小实现

```ts
export class Context {
  private services = new Map<string, unknown>()

  provide(name: string, service: unknown): void {
    this.services.set(name, service)
  }

  get(name: string): unknown {
    return this.services.get(name)
  }

  has(name: string): boolean {
    return this.services.has(name)
  }

  remove(name: string): void {
    this.services.delete(name)
  }
}
```

## 测试

```ts
describe('Service Removal', () => {
  it('has() 在 provide 之后为 true，remove 之后为 false', () => {
    const ctx = new Context()
    const greeter = { greet: (name: string) => `Hello, ${name}!` }

    expect(ctx.has('greeter')).toBe(false)
    ctx.provide('greeter', greeter)
    expect(ctx.has('greeter')).toBe(true)

    ctx.remove('greeter')
    expect(ctx.has('greeter')).toBe(false)
  })

  it('remove 之后 get 返回 undefined', () => {
    const ctx = new Context()
    ctx.provide('greeter', { greet: (name: string) => `Hello, ${name}!` })
    ctx.remove('greeter')
    expect(ctx.get('greeter')).toBeUndefined()
  })

  it('remove 一个从未 provide 过的 name 不报错', () => {
    const ctx = new Context()
    expect(() => ctx.remove('does-not-exist')).not.toThrow()
  })
})
```

## Demo

```ts
import { Context } from './src/context'

const ctx = new Context()
const greeter = { greet(name: string) { return `Hello, ${name}!` } }

ctx.provide('greeter', greeter)
console.log('has before remove:', ctx.has('greeter'))

ctx.remove('greeter')
console.log('has after remove:', ctx.has('greeter'))
console.log('get after remove:', ctx.get('greeter'))
```

实际输出：

```text
has before remove: true
has after remove: false
get after remove: undefined
```

## 这一章之后

- `remove()` 只是把 service 从 `Map` 里删掉，没有任何"通知"机制——如果有别的代码正持有这个 service 的引用，或者依赖它存在，`remove()` 完全不会告诉它们。这正是后面 Effect 和 Reactive Dependency Lifecycle 要解决的问题。
- 没有"谁 provide 的、谁应该负责 remove"这种归属关系——任何代码都可以 `remove` 任何 service，不需要证明自己有权限。Ownership 是 Plugin Scope 那一章才引入的概念。

## 思考题

1. `has()` 和 `get(name) !== undefined` 在效果上是等价的（本章的实现里，`services.get()` 对不存在的 key 就是返回 `undefined`）。既然如此，为什么还要专门加一个 `has()` 方法？如果 service 本身的值可以合法地是 `undefined`（比如 `ctx.provide('flag', undefined)`），这两种判断方式还等价吗？
2. `remove()` 对不存在的 name 是安全的 no-op。设想一下，如果改成"remove 不存在的 name 时抛异常"，会给上层调用方增加什么负担？
3. 这一章说"任何代码都可以 remove 任何 service，没有 ownership 检查"。你觉得这在什么场景下会成为一个真实的 bug 来源？留着这个问题，等 Plugin Scope 那一章实现后回头看是怎么解决它的。
