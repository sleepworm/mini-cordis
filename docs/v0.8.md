# v0.8 — Dependency Check

## 这一章解决什么问题

到目前为止，如果一个 Plugin 想用另一个 Plugin 提供的 service，唯一的办法是自己 `ctx.get(name)`，然后自己判断"这个东西存不存在"（`if (!ctx.get('clock')) { ... }`）——这种判断散落在每个用到依赖的地方，没有一个统一的、声明式的方式说"我需要这些东西才能工作"。这一章加入 `ctx.require()`，第一次显式建立"谁依赖谁"这件事。

## 上一版本有什么不足

设想一个 `farewell` 模块要依赖 `clock` 才能工作，用上一章为止的工具，只能这样写：

```ts
const farewellPlugin: Plugin = (ctx) => {
  if (!ctx.has('clock')) {
    throw new Error('clock is required') // 或者悄悄不做任何事，行为不明确
  }
  ctx.provide('farewell', { ... })
}
```

这种写法每个依赖方都要重新发明一遍，而且"不存在时该怎么办"完全没有统一约定——有的可能抛异常，有的可能静默跳过，行为不可预测。

## 本章设计

最小的依赖检查 API：

```ts
ctx.require(['greeter'], (ctx) => {
  // 只有 greeter 存在时才会跑到这里
})
```

**这一版故意不做动态恢复**——只回答一个问题：**此刻**，这些依赖都在吗？

- 都在 → 执行 callback
- 有任何一个不在 → **抛出一个明确的 `MissingDependencyError`**，callback 完全不执行

```ts
export class MissingDependencyError extends Error {
  constructor(public readonly missing: string[]) {
    super(`missing dependency: ${missing.join(', ')}`)
    this.name = 'MissingDependencyError'
  }
}
```

选择"抛异常"而不是"静默不执行"，是为了让"依赖没准备好"这件事在这一章**必须被显式处理**，不能被意外忽略——这是刻意的教学设计，不是最终答案。等到下一章引入动态 Lifecycle 之后，"依赖不存在"会变成一个可以被优雅处理的运行时状态（callback 被推迟执行，而不是报错），到时候 `require()` 这种"立即检查、不满足就报错"的用法会显得过于死板——这正是下一章要对比、要升级的地方。

### 为什么先这样：把"静态检查"和"动态 Lifecycle"拆成两个 commit

如果这一章直接实现"依赖出现就自动激活、消失就自动失效"，会把两件不同的事情糅在一起：**"依赖此刻是否满足"是一个可以立刻回答的问题**（有 or 没有），**"依赖满足与否会随时间变化，组件要跟着响应"**则是一个全新的、需要在 Context 里维护额外状态和监听机制的问题。先把前者做对、做扎实，再叠加后者，比一步到位更容易看清楚每一层到底在解决什么。

## 最小实现

`src/dependency.ts`：

```ts
export class MissingDependencyError extends Error {
  constructor(public readonly missing: string[]) {
    super(`missing dependency: ${missing.join(', ')}`)
    this.name = 'MissingDependencyError'
  }
}
```

`src/context.ts` 新增：

```ts
require(names: string[], callback: (ctx: Context) => void): void {
  const missing = names.filter((name) => !this.has(name))
  if (missing.length) {
    throw new MissingDependencyError(missing)
  }
  callback(this)
}
```

`missing` 收集**所有**缺失的依赖，不是找到第一个就报错——这样错误信息一次性告诉调用方"你还差哪些东西"，不用一次改一个、反复重试才发现下一个也缺。

## 测试

```ts
it('依赖不存在时，抛出 MissingDependencyError，callback 不执行', () => {
  const ctx = new Context()
  let ran = false

  expect(() => {
    ctx.require(['greeter'], () => { ran = true })
  }).toThrow(MissingDependencyError)

  expect(ran).toBe(false)
})

it('错误里列出所有缺失的依赖，不只是第一个', () => {
  const ctx = new Context()
  ctx.provide('greeter', {})
  // 'clock' 和 'logger' 都缺失，'greeter' 存在

  try {
    ctx.require(['greeter', 'clock', 'logger'], () => {})
    expect.unreachable()
  } catch (error) {
    expect(error).toBeInstanceOf(MissingDependencyError)
    expect((error as MissingDependencyError).missing).toEqual(['clock', 'logger'])
  }
})
```

运行：

```bash
npm test
```

实际输出：

```text
 Test Files  8 passed (8)
      Tests  32 passed (32)
```

## Demo

```ts
import { Context } from './src/context'

const ctx = new Context()

try {
  ctx.require(['greeter'], () => {
    console.log('greeter is ready')
  })
} catch (error: any) {
  console.log('error:', error.message)
}

ctx.provide('greeter', { greet(name: string) { return `Hello, ${name}!` } })

ctx.require(['greeter'], (ctx) => {
  const greeter = ctx.get('greeter') as any
  console.log(greeter.greet('Alex'))
})
```

实际输出：

```text
error: missing dependency: greeter
Hello, Alex!
```

第一次 `require` 时 `greeter` 还没 `provide`，`catch` 到 `MissingDependencyError`；`provide` 之后第二次 `require` 正常执行，打印出 `Hello, Alex!`。

## 这一章之后

- **依赖关系没有被记住**：`require()` 检查完这一次就完事了，Context 完全不知道"这个 callback 依赖过 greeter"这件事。如果之后 `greeter` 被 `remove()`，已经跑过的 callback 不会有任何反应——这就是为什么这一版"暂时不做动态恢复"。
- **没有和 `plugin()`/`effect()` 打通**：`require()` 目前是一个独立的方法，和前几章建立的 scope/effect 机制没有关联。下一章会让依赖检查真正融入 Plugin 的生命周期。
- **`ctx.require()` 抛异常的方式，对"依赖一开始就不满足，之后可能会满足"这种场景不友好**——调用方要么提前反复检查、要么用 try/catch 包一层重试逻辑，这两种做法都很笨拙。这正是下一章要解决的核心问题。

## 思考题

1. `require()` 选择"依赖不满足就抛异常"而不是"静默不执行 callback"。如果 MiniCordis 到此为止就不再往前推进了（不做动态恢复），你觉得这个选择是不是一个好的最终设计？为什么？
2. 设想一个 Plugin 同时 `require(['clock', 'clock'])`（写重复了）——现在的实现会有什么行为？这算不算一个需要专门处理的边界情况？
3. `missing` 数组按 `names` 里传入的原始顺序收集，还是有其他顺序？这个顺序会不会影响错误信息对调用方的可读性？如果 `require(['logger', 'clock', 'greeter'])` 只有 `clock` 缺失，错误信息会是什么？
