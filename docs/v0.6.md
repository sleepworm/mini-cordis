# v0.6 — Plugin Scope

## 这一章解决什么问题

上一章的 `ctx.dispose()` 是"一锅端"——不管一个 Context 上装了多少 Plugin，`dispose()` 一次性把所有 effect 全部撤销。这一章要做到：

```ts
const disposeGreeter = ctx.plugin(greeterPlugin)
disposeGreeter()
```

只撤销 `greeterPlugin` 自己造成的改变，其他 Plugin 不受影响。

## 上一版本有什么不足

上一章结尾已经指出了这个问题：`greeterPlugin` 和 `loggerPlugin` 如果都用 `ctx.effect()`，它们的 cleanup 会被塞进同一个 `this.cleanups` 数组，谁也分不清哪个 cleanup 属于哪个 Plugin。想只卸载 Greeter、保留 Logger，在上一版里做不到——`dispose()` 只有"全部撤销"一种粒度。

## 本章设计

核心思路：**每次 `ctx.plugin()` 都开一个独立的 Effect Scope**，这个 Plugin 内部所有 `ctx.effect()` 注册的 cleanup 都记到这个 scope 里，不再和别的 Plugin 混在一起：

```text
Context
├── Plugin Scope A
│    ├── effect
│    └── effect
│
└── Plugin Scope B
     ├── effect
     └── effect
```

`ctx.plugin(fn)` 的返回值从 `void` 变成一个只属于这次安装的 `dispose` 函数。

### 怎么知道"现在该记到哪个 scope"

`Context` 维护一个 `currentScope` 指针，默认指向根级别的 `cleanups`。`plugin(fn)` 执行期间，把 `currentScope` 临时指向这个 Plugin 自己的新 scope，`fn(ctx)` 内部所有的 `ctx.effect()` 调用因此都记到了正确的地方；`fn` 跑完（不管成功还是抛错，用 `finally`）把 `currentScope` 指回原来的值。

```ts
plugin(fn: Plugin): () => void {
  const parentScope = this.currentScope
  const scope: Cleanup[] = []

  this.currentScope = scope
  try {
    fn(this)
  } finally {
    this.currentScope = parentScope
  }

  // ...
}
```

### 怎么让 ctx.dispose() 仍然能"全部撤销"

关键的一步：把这个 Plugin 的 `dispose` 函数本身，注册成**父 scope 的一个 cleanup**：

```ts
parentScope.push(dispose)
return dispose
```

这样一来：

- 单独调用 `disposeGreeter()`——只撤销 Greeter 自己 scope 里的东西。
- 调用根级别的 `ctx.dispose()`——它撤销根 scope 的所有 cleanup，而 Greeter 的 `dispose` 函数本身就是根 scope 里的一个 cleanup，所以会被级联调用，等效于"撤销了整个 Greeter scope"。

`dispose` 函数内部有一个 `disposed` 标志位保证幂等：不管是被外部直接调用，还是被父 scope 级联调用，重复触发都是安全的 no-op（延续前几章定下的"重复撤销不报错、不重复执行副作用"的一致原则）。

## 最小实现

```ts
export class Context {
  private services = new Map<string, unknown>()
  private cleanups: Cleanup[] = []
  private currentScope: Cleanup[] = this.cleanups

  // ...provide / get / has / remove 不变

  effect(setup: EffectSetup): void {
    const cleanup = setup()
    if (cleanup) {
      this.currentScope.push(cleanup)
    }
  }

  plugin(fn: Plugin): () => void {
    const parentScope = this.currentScope
    const scope: Cleanup[] = []

    this.currentScope = scope
    try {
      fn(this)
    } finally {
      this.currentScope = parentScope
    }

    let disposed = false
    const dispose = () => {
      if (disposed) return
      disposed = true
      while (scope.length) {
        scope.pop()!()
      }
    }

    parentScope.push(dispose)
    return dispose
  }

  dispose(): void {
    while (this.cleanups.length) {
      this.cleanups.pop()!()
    }
  }
}
```

`effect()` 只改了一行——从写死 `this.cleanups.push` 变成 `this.currentScope.push`；`plugin()` 是这一章唯一实质性变化的地方。

## 测试

```ts
it('卸载 A 不影响 B（Effect Scope 是独立的）', () => {
  const ctx = new Context()

  const pluginA: Plugin = (ctx) => {
    ctx.effect(() => {
      ctx.provide('a', 'service-a')
      return () => ctx.remove('a')
    })
  }
  const pluginB: Plugin = (ctx) => {
    ctx.effect(() => {
      ctx.provide('b', 'service-b')
      return () => ctx.remove('b')
    })
  }

  const disposeA = ctx.plugin(pluginA)
  ctx.plugin(pluginB)

  disposeA()

  expect(ctx.has('a')).toBe(false)
  expect(ctx.has('b')).toBe(true)
})
```

（完整测试见 `test/plugin-scope.test.ts`，还覆盖了"`ctx.dispose()` 仍然级联撤销所有 plugin"、"单个 plugin 的 dispose 重复调用安全"、"先手动 dispose 一个 plugin，之后 `ctx.dispose()` 不重复执行"几个场景。）

npm test
```

      Tests  23 passed (23)
```

## Demo

```ts
import { Context } from './src/context'
import type { Plugin } from './src/plugin'

const pluginA: Plugin = (ctx) => {
  ctx.effect(() => {
    ctx.provide('a', 'service-a')
    return () => ctx.remove('a')
  })
}
const pluginB: Plugin = (ctx) => {
  ctx.effect(() => {
    ctx.provide('b', 'service-b')
    return () => ctx.remove('b')
  })
}

const ctx = new Context()
const disposeA = ctx.plugin(pluginA)
ctx.plugin(pluginB)

console.log('before disposeA — a:', ctx.has('a'), 'b:', ctx.has('b'))
disposeA()
console.log('after disposeA  — a:', ctx.has('a'), 'b:', ctx.has('b'))
```

实际输出：

```text
before disposeA — a: true b: true
after disposeA  — a: false b: true
```

## 这一章之后

- `plugin()` 内部把自己的 `dispose` 塞进 `parentScope` 这个实现方式，顺带就支持了"Plugin 里再调用 `ctx.plugin()`"（嵌套 Plugin）——但这一章没有为嵌套场景专门写测试，行为没有被显式验证过，只是设计上恰好没有排除它。
- 没有办法查询"这个 scope 里现在有哪些 effect"，出了问题只能靠打断点。
- Ownership 目前只体现在"谁的 cleanup 记在谁的 scope 里"，没有更进一步的"这个 service 是谁提供的、别人能不能覆盖它"这类检查——上一章思考题提出的"两个 Plugin 名字撞了怎么办"，这一章仍然没有回答。

## 思考题

1. 如果 `plugin()` 不把自己的 `dispose` 塞进 `parentScope`，只是简单地 `return dispose`，`ctx.dispose()` 还能级联撤销所有 Plugin 吗？为什么？
2. 这一章的 `dispose` 函数用了一个 `disposed` 布尔标志位防止重复执行。如果去掉这个标志位，"先手动 `disposeA()`，再调用 `ctx.dispose()`"这个场景会出什么问题？
3. 试着不看代码，自己写一版"Plugin 内部再调用 `ctx.plugin()`"的测试用例，预测外层 `dispose()` 之后内层 Plugin 的 service 是否也会消失。写完之后实际跑一遍，看看和你的预期是否一致（这是验证"设计上支持但没测试过"的行为是否真的可靠的好方法）。
