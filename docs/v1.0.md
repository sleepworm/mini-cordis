# v1.0 — HelloCordis Final Demo

> 这就是整个 MiniCordis 项目的"期末考试"。

## 这一章解决什么问题

前面 11 章逐一实现了 Context、Service Registry、Plugin、Effect、Plugin Scope、Event、Dependency Check、Reactive Dependency Lifecycle、Failure Isolation、Child Context——每一章只验证一个概念，用的都是最小化的例子。这一章要回答：**这些机制拼在一起，能不能撑起一个像 HelloCordis 那样的真实场景？**

## 上一版本有什么不足

到上一章为止，MiniCordis 的每个测试都是孤立的、针对单一机制的。从没有一次性把 Plugin、Effect、Event、响应式依赖全部用在同一个、有实际意义的场景里——没有验证过"这些机制放在一起会不会打架"。

## 本章设计

不新增任何 API。这一章是纯粹的集成验证：用 MiniCordis 现有的全部机制，重新实现一遍 HelloCordis 场景——`examples/hello-cordis/`，直接 `import` `src/index.ts`，不需要单独的 package/node_modules。

组件：

```text
EnglishGreeter Plugin
ChineseGreeter Plugin
App Plugin
Logger Plugin
Analytics Plugin
```

完整流程：

```text
Context start
   ↓
Logger installed
   ↓
App waits for greeter
   ↓
EnglishGreeter installed
   ↓
App activates
   ↓
Hello, Alex!
   ↓
greet event
   ↓
Logger receives
   ↓
EnglishGreeter unload
   ↓
App deactivates
   ↓
ChineseGreeter installed
   ↓
App activates again
   ↓
你好，Alex！
```

### 每个组件用到了哪些机制

- **EnglishGreeter / ChineseGreeter**：`ctx.plugin()` + `ctx.effect()`，setup 时 `provide('greeter', ...)`，cleanup 时 `remove('greeter')`。
- **App**：`ctx.inject(['greeter'], callback)`——这是全篇最大的一个对比点：一个手写的、只在乎"能力可能不存在"的 App，需要自己写 `if (!ctx.greeter) { ... return }`；这里完全不需要，依赖满足/消失由 MiniCordis 自动响应。
- **Logger / Analytics**：`ctx.on('greet', ...)`，互相之间、和 App/Greeter 之间都不知道对方存在。
- **卸载 EnglishGreeter、重装 ChineseGreeter**：`ctx.plugin()` 返回的 `dispose()`，App 的 deactivate/reactivate 全部自动发生，靠的是响应式依赖机制。

## 最小实现

`examples/hello-cordis/app.ts`——和一个手写版本的 App 对比，能直接看出响应式依赖省掉了什么：

```ts
import type { Plugin } from '../../src/index'

// App 完全不 import 具体的 Greeter 实现，只用 ctx.inject() 声明依赖 'greeter'。
// 依赖满足时自动打招呼、自动 emit('greet')；依赖消失时自动"停摆"——
// 不需要手写 if (!ctx.greeter) 判断。
export const app: Plugin = (ctx) => {
  ctx.inject(['greeter'], (ctx) => {
    const greeter = ctx.get('greeter') as { greet(name: string): string }
    const message = greeter.greet('Alex')
    console.log('[App]', message)
    ctx.emit('greet', 'Alex')

    ctx.effect(() => {
      return () => {
        console.log('[App] deactivated (greeter unavailable)')
      }
    })
  })
}
```

`examples/hello-cordis/index.ts` 编排整个流程：

```ts
import { Context } from '../../src/index'
import { englishGreeter } from './english-greeter'
import { chineseGreeter } from './chinese-greeter'
import { logger } from './logger'
import { analytics } from './analytics'
import { app } from './app'

function main() {
  console.log('=== Context start ===')
  const ctx = new Context()

  console.log('\n=== Logger + Analytics installed ===')
  ctx.plugin(logger)
  ctx.plugin(analytics)

  console.log('\n=== App installed (waits for greeter) ===')
  ctx.plugin(app)

  console.log('\n=== EnglishGreeter installed ===')
  const disposeEnglish = ctx.plugin(englishGreeter)

  console.log('\n=== EnglishGreeter unloaded ===')
  disposeEnglish()

  console.log('\n=== ChineseGreeter installed ===')
  ctx.plugin(chineseGreeter)
}

main()
```

`englishGreeter`/`chineseGreeter`/`logger`/`analytics` 分别是四个独立文件，每个都只做前面章节教过的事——Greeter 用 `ctx.effect()` 包一层 `provide`/`remove`，`logger`/`analytics` 都是一行 `ctx.on('greet', ...)`。

## 这一章之后：MiniCordis 到这里做到了什么、没做到什么

- ✅ 响应式依赖生命周期（v0.9）——已解决，这一章的 App 就是证据。
- ✅ Plugin 失败隔离（v0.10）——已解决。
- ✅ Child Context 的继承/隔离基础版（v0.11）——已解决。
- ❌ Isolation、Intercept——从一开始就没打算做进 MiniCordis 第一阶段。
- ❌ 类型系统联动（`declare module` 扩展）——`ctx.get()` 返回 `unknown`，`app.ts` 里还在手动 `as { greet(name: string): string }`。
- ❌ Plugin 支持 class/`{ apply }` 形态——仍然只有函数。
- ❌ 更精细的事件分发语义（`parallel`/`serial`/`bail`/`waterfall` 之类）——`emit()` 还是最基础的同步广播。

这些不是"没做完"，是从一开始就明确划出的范围——MiniCordis 的目标是吃透 Runtime 模型，不是复刻一个生产级框架的每一个细节。

## 全书结论

`examples/hello-cordis/` 和真实场景里"App 不应该依赖具体 Greeter 实现"这个约束是同一件事，唯一的区别是这一版的 App 用 `ctx.inject()` 替代了手写的 `if (!ctx.greeter)` 判断。这个对比本身就是全书最好的总结：**价值不在于 API 有多花哨，而在于"依赖是运行时状态、能力会自动响应生命周期变化"这套模型**——MiniCordis 用不到 200 行核心代码，把这套模型从零实现了一遍，也就真正理解了它。
