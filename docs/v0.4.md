# v0.4 — Plugin Install

## 这一章解决什么问题

到目前为止，注册一个 service 靠的是直接调用 `ctx.provide(name, service)`——调用方要自己构造好 service 对象，自己想好起什么名字。这一章引入 **Plugin**：一个"知道怎么给 Context 安装能力"的独立单元，调用方只需要 `ctx.plugin(xxx)`，不需要关心内部具体 `provide` 了什么、怎么 `provide` 的。

## 上一版本有什么不足

`ctx.provide('greeter', { greet: ... })` 这种写法，把"定义 greeter 长什么样"和"把 greeter 装进这个 Context"这两件事混在了调用现场，没法复用、没法在多个 Context 之间共享同一份"安装逻辑"，也没有一个统一的"单元"概念。

## 本章设计

最小的 Plugin 类型：

```ts
export type Plugin = (ctx: Context) => void
```

**Plugin 就是一个接受 `ctx` 的函数**，函数体内部想对 `ctx` 做什么都可以——最常见的是调用 `ctx.provide(...)` 挂一个 service，但这不是强制的。

`Context.plugin()` 的实现极简：

```ts
plugin(fn: Plugin): void {
  fn(this)
}
```

### 本章核心：Plugin ≠ Service

这是这一章唯一要真正想清楚的事：

> Plugin 是"对 Context 施加一组改变的安装单元"；Service 只是它可能带来的一个效果。

`greeterPlugin` 这个 Plugin 的效果是"往 `ctx` 里塞了一个 `greeter` service"，但 Plugin 本身不等于这个 service——一个 Plugin 完全可以什么 service 都不 `provide`，只是做点别的事（后面章节的 Logger Plugin 就是这样：它不提供任何 service，只是订阅一个事件）。把这两个概念分开，是为了让"安装单元"和"它安装的东西"能独立演化。

## 最小实现

`src/plugin.ts`：

```ts
import { Context } from './context'

export type Plugin = (ctx: Context) => void
```

`src/context.ts` 新增：

```ts
import type { Plugin } from './plugin'

export class Context {
  // ...既有的 services / provide / get / has / remove

  plugin(fn: Plugin): void {
    fn(this)
  }
}
```

`context.ts` 用 `import type` 引用 `Plugin`：`plugin.ts` 需要引用 `Context` 类型，`context.ts` 又需要引用 `Plugin` 类型，两个文件互相引用对方——用类型导入让这个引用只在编译期存在，不会产生真正的运行时循环 `import`，避免 ESM 循环依赖的初始化顺序问题。

## 测试

```ts
describe('Plugin', () => {
  it('plugin 函数会被调用，并收到 ctx', () => {
    const ctx = new Context()
    let received: Context | undefined
    ctx.plugin((ctx) => { received = ctx })
    expect(received).toBe(ctx)
  })

  it('plugin 可以通过 ctx.provide 向 Context 注册能力', () => {
    const ctx = new Context()
    ctx.plugin((ctx) => {
      ctx.provide('greeter', { greet: (name: string) => `Hello, ${name}!` })
    })
    const greeter = ctx.get('greeter') as { greet(name: string): string }
    expect(greeter.greet('Alex')).toBe('Hello, Alex!')
  })

  it('可以安装多个 plugin，互不干扰', () => {
    const ctx = new Context()
    ctx.plugin((ctx) => ctx.provide('greeter', { greet: (n: string) => `Hello, ${n}!` }))
    ctx.plugin((ctx) => ctx.provide('logger', { log: (m: string) => m }))
    expect(ctx.has('greeter')).toBe(true)
    expect(ctx.has('logger')).toBe(true)
  })
})
```

运行：

```bash
npm test
```

实际输出：

```text

      Tests  12 passed (12)
```

## Demo

```ts
import { Context } from './src/context'
import type { Plugin } from './src/plugin'

const greeterPlugin: Plugin = (ctx) => {
  ctx.provide('greeter', {
    greet(name: string) { return `Hello, ${name}!` }
  })
}

const ctx = new Context()
ctx.plugin(greeterPlugin)

console.log((ctx.get('greeter') as any).greet('Alex'))
```

实际输出：

```text
Hello, Alex!
```

## 这一章之后

- `ctx.plugin(fn)` 没有返回值——装完就完了，没法"撤销"这次安装。因为 Plugin 内部调用的 `ctx.provide(...)` 没有留下任何"怎么撤销"的记录。这是下一章（Reversible Effect）要解决的。
- Plugin 之间没有隔离——`greeterPlugin` 和 `loggerPlugin` 装的东西都直接进了同一个 `services` Map，一个 Plugin 理论上可以看到、甚至覆盖另一个 Plugin provide 的 service。Ownership/Scope 是后面章节的内容。
- Plugin 只能是普通函数——这里先只做最简单的函数形态，不支持 class 或带 `apply` 方法的对象。

## 思考题

1. 如果 `ctx.plugin(fn)` 的实现不是 `fn(this)` 而是 `fn(new Context())`（传一个新的空 Context 进去），会发生什么？为什么这个设计选择对"Plugin 能够修改调用方的 Context"这件事至关重要？
2. 本章说"Plugin 完全可以什么 service 都不 provide"。想一个只做别的事、不提供任何 service 的 Plugin 的例子（不一定要写代码，说清楚它会做什么）。
3. `greeterPlugin` 和 `loggerPlugin` 现在共享同一个 `ctx`，没有任何隔离。如果 `loggerPlugin` 不小心写成 `ctx.provide('greeter', ...)`（名字撞了），会发生什么？结合上一章"重复 provide 直接覆盖"的策略，这个 bug 会有多难排查？
