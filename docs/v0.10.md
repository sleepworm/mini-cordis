# v0.10 — Plugin Failure Isolation

## 这一章解决什么问题

到目前为止，所有测试和 Demo 里的 Plugin/Effect/Injection callback 都假设"代码不会出错"。这一章要回答：**如果一个 Plugin 的 setup 或 cleanup 抛异常，Runtime 应该怎么反应？** 目标是：

```text
Plugin A fail
   ↓
不要破坏 Plugin B
```

## 上一版本有什么不足

现在 `runInScope()` 跑 `fn(this)` 没有任何 try/catch——如果 `fn` 抛错：

- `plugin(fn)` 会直接把异常甩给调用方，调用方的脚本如果没有自己包 try/catch，整个程序崩溃，后面排队要装的 `pluginB` 根本没机会运行。
- 更隐蔽的问题在 `dispose()`：LIFO 循环 `while (scope.length) { scope.pop()!() }` 如果某一个 cleanup 抛错，循环立刻中断，**排在它后面（更早注册）的 cleanup 全部不会执行**——这不只是"这一个 Plugin 没清理干净"，因为一个 Plugin 的 `dispose` 函数本身又是父 scope 里的一个 cleanup 条目，它抛错还会连累父 scope 循环里排在它后面的**其他 Plugin** 的 dispose 也不会被调用。这才是真正需要隔离的地方。

## 本章设计

三条明确的要求，这一章逐条对应实现：

1. **effect cleanup 尽可能执行**
2. **错误可被上层观察**
3. **其他 scope 不被错误清空**

### 关键决策：把"循环撤销"单独抽成一个永不抛错的方法

新增 `teardown(scope)`，替代原来两处重复的 LIFO 循环（`dispose()` 和 `runInScope()` 返回的 dispose 函数）：

```ts
private teardown(scope: Cleanup[]): void {
  while (scope.length) {
    const cleanup = scope.pop()!
    try {
      cleanup()
    } catch (error) {
      this.reportError(error)
    }
  }
}
```

单个 `cleanup()` 抛错被 `catch` 住、上报，循环继续处理剩下的——这同时满足要求 1（尽可能执行）和要求 3（不影响其他）：因为一个 Plugin 的 `dispose` 本身现在也遵守"我永远不抛错，出错自己处理掉"这条规则，它作为父 scope 里的一个 cleanup 条目被调用时，即使内部出了问题，也不会让父 scope 的 `teardown` 循环中断——兄弟 Plugin 的 dispose 照常执行。

### 错误怎么被"上层观察"到

复用已经有的 Event Bus，而不是发明新机制：

```ts
private reportError(error: unknown): void {
  this.emit('error', error)
}
```

想观察错误的调用方，直接 `ctx.on('error', (error) => { ... })` 就行——这是本书第一次让"新功能"完全建立在已有机制之上，不新增任何 API 表面。

### setup 阶段出错：回滚 + 上报，返回一个"空" dispose

```ts
private runInScope(fn: (ctx: Context) => void): () => void {
  const parentScope = this.currentScope
  const scope: Cleanup[] = []

  this.currentScope = scope
  try {
    fn(this)
  } catch (error) {
    this.currentScope = parentScope
    this.teardown(scope)      // 回滚已经注册的那部分 effect
    this.reportError(error)   // 上报
    return () => {}           // 调用方（plugin()）仍然拿到一个可调用的 dispose，只是它是空操作
  }
  this.currentScope = parentScope

  let disposed = false
  return () => {
    if (disposed) return
    disposed = true
    this.teardown(scope)
  }
}
```

`plugin(fn)` 和 `activate(injection)` **完全不需要改动**——它们只是调用 `runInScope()` 拿到一个 dispose 函数，至于这个 dispose 函数背后是"正常激活"还是"出错后回滚"，对它们来说是透明的。这是延续上一章就定下的设计红利：把"打开 scope、跑代码、记住怎么撤销"这件事收敛到一个地方，任何加固都只需要改一处。

## 最小实现

除了上面两个方法，`dispose()` 也顺手用上了 `teardown()`：

```ts
dispose(): void {
  this.teardown(this.cleanups)
}
```

三处重复的 LIFO 循环，现在只有一处实现。

## 测试

```ts
it('Plugin A 安装失败，不影响 Plugin B 正常安装', () => {
  const ctx = new Context()
  ctx.on('error', () => {})

  ctx.plugin(() => { throw new Error('plugin A failed') })
  ctx.plugin((ctx) => ctx.provide('b', 'service-b'))

  expect(ctx.has('b')).toBe(true)
})

it('plugin 安装时半途抛错，之前已经注册的 effect 会被回滚', () => {
  const ctx = new Context()
  ctx.on('error', () => {})

  ctx.plugin((ctx) => {
    ctx.effect(() => {
      ctx.provide('a', 'service-a')
      return () => ctx.remove('a')
    })
    throw new Error('boom after registering a')
  })

  expect(ctx.has('a')).toBe(false) // 已回滚，没有遗留
})

it('dispose 阶段某个 plugin 的 cleanup 抛错，不影响另一个 plugin 的 cleanup 执行', () => {
  const ctx = new Context()
  ctx.on('error', () => {})
  const cleaned: string[] = []

  ctx.plugin((ctx) => ctx.effect(() => () => { throw new Error('A cleanup failed') }))
  ctx.plugin((ctx) => ctx.effect(() => () => cleaned.push('B cleaned up')))

  ctx.dispose()

  expect(cleaned).toEqual(['B cleaned up']) // A 出错不连累 B
})
```

运行：

```bash
npm test
```

实际输出：

```text
 Test Files  10 passed (10)
      Tests  46 passed (46)
```

## Demo

```ts
import { Context } from './src/context'
import type { Plugin } from './src/plugin'

const ctx = new Context()
ctx.on('error', (error: any) => {
  console.log('[error]', error.message)
})

const brokenPlugin: Plugin = () => {
  throw new Error('plugin A failed')
}
const goodPlugin: Plugin = (ctx) => {
  ctx.provide('greeter', { greet(name: string) { return `Hello, ${name}!` } })
}

console.log('--- installing broken plugin ---')
ctx.plugin(brokenPlugin)

console.log('--- installing good plugin ---')
ctx.plugin(goodPlugin)

console.log('has greeter:', ctx.has('greeter'))
console.log((ctx.get('greeter') as any).greet('Alex'))
```

实际输出：

```text
--- installing broken plugin ---
[error] plugin A failed
--- installing good plugin ---
has greeter: true
Hello, Alex!
```

`brokenPlugin` 抛出的异常没有让脚本崩溃，`goodPlugin` 照常正常工作。

## 这一章之后

- 没有重试机制——一个 Plugin 失败了就是失败了，不会自动重装。
- 如果 `ctx.on('error', ...)` 本身的 listener 又抛错，会发生什么？`emit()` 里的 `for...of` 循环没有 try/catch，这个错误会直接冒出来——这是一个没处理的"元错误"场景，教学阶段先不管。
- 没有区分"setup 失败"和"cleanup 失败"这两种错误的严重程度——两者都只是简单地 `emit('error', error)`，调用方拿到的错误对象里没有任何"这是安装失败还是清理失败"的元信息，需要自己从错误消息里猜。
- 如果没有任何代码 `ctx.on('error', ...)`，错误会被 `reportError` 静默吞掉（`emit` 对没有 listener 的事件是 no-op）——这在开发阶段可能会隐藏真实的 bug。

## 思考题

1. `runInScope()` 在 setup 失败时会 `teardown(scope)` 回滚部分注册的 effect。如果这个回滚过程本身又抛错（某个 cleanup 出错），会发生什么？追踪一下代码路径确认你的答案。
2. 现在的设计里，如果没有任何人 `ctx.on('error', ...)`，所有错误都被静默吞掉。你觉得这是不是一个好的默认行为？如果要仿照大多数事件系统"没有 listener 就直接抛出"的做法，应该怎么改 `reportError()`？这样改了之后，之前所有没有注册 `'error'` listener 的测试用例，行为会不会被破坏？
3. `teardown()` 现在的错误处理是"抓住、上报、继续"，不区分错误的来源和严重程度。设想一个场景：一个 Plugin 卸载时，它的 cleanup 抛错，原因是"这个 cleanup 依赖的另一个资源已经不存在了"——这种错误值得终止整个 dispose 流程吗？为什么现在的设计选择了"绝不因为一个错误终止整体流程"？
